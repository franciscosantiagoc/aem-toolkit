# AEM Toolkit — Especificación funcional y roadmap

> Extensión de VS Code para acelerar el desarrollo en proyectos AEM (arquetipo Maven estándar: `core` / `ui.apps` / `ui.content` / `ui.config` / `ui.frontend` opcional / `dispatcher` / `all`). Este archivo es la fuente de verdad de todo lo que se va a construir, para que ninguna idea se pierda entre bloques. Se actualiza en cada bloque: lo hecho se marca `[x]`, lo pendiente queda `[ ]`.
>
> Proyectos de referencia analizados: **gatesconnect-aem**, **gnp-solvimas**, **Repsol-Lubricantes** (y `repsol-portugal`/`gnp-dispatcher`/`gates-aem-dispatcher` como dispatchers hermanos). Todos comparten el arquetipo Maven de Adobe: módulos `all/core/ui.apps/ui.apps.structure/ui.config/ui.content/it.tests/ui.tests`, con `ui.frontend` presente solo en algunos (ej. gatesconnect-aem y gnp-solvimas sí lo tienen; Repsol-Lubricantes no) — la extensión debe **detectar** esto en vez de asumirlo.

## 0. Arquitectura de la extensión

Se sigue el mismo patrón que ya usas en `angular-schematics-free` (mismo repo `extensiones-visual-studio`, rama `feature/aem-toolkit`):

- TypeScript + `vscode` API, compilado con `tsc`, empaquetado con `@vscode/vsce` (`npm run package` → `.vsix`).
- Icono propio en la **barra de actividad** (izquierda, junto a Explorador/Extensiones) con un `viewsContainers.activitybar`, y una vista de árbol (`TreeDataProvider`) que expone todos los comandos organizados por categoría — igual que el árbol "Generadores" de Angular Schematics Free.
- Un comando por funcionalidad (para Command Palette y `keybindings`), con clausulas `when` para que solo aparezcan donde tienen sentido (ej. "Nuevo componente" solo sobre carpetas dentro de `ui.apps/.../components`).
- **Menús contextuales agrupados en un solo submenú "AEM Toolkit"** (v1.7.1, a pedido explícito): en vez de que cada comando aparezca como una entrada suelta en `explorer/context`/`editor/context` (lo que daba la impresión de ser varias extensiones distintas), todos quedan bajo un único submenú desplegable "AEM Toolkit" — vía la contribución `submenus` de `package.json`, un id distinto por contexto (`aemToolkit.explorerMenu`, `aemToolkit.editorMenu`) ya que cada uno lista comandos distintos con sus propias `when`. Dentro del submenú se mantienen agrupados por sección con un prefijo numérico en el `group` (`1_build`, `2_sync`, `3_dialog`, `4_format`) para conservar el orden visual de siempre.
- `config.ts` centraliza toda la configuración (`aemToolkit.*` en `settings.json`), igual que `angularSchematicsFree.*`.
- **Buscador/filtro en todas las listas de selección**: cualquier `QuickPick` con más de ~6 opciones (componentes existentes, plantillas, campos de diálogo, perfiles Maven, idiomas, tags…) usa `vscode.window.showQuickPick` con `matchOnDescription`/`matchOnDetail` activados y una `placeHolder` que invite a escribir para filtrar. Para selecciones más ricas (formularios de content fragment, tags, diálogos) se usa un **Webview** con un `<input>` de filtro en vivo sobre listas largas (tipos de campo, componentes del proyecto, idiomas).

## 1. Roadmap por bloques (reordenado en v2.0.0 por prioridad de construcción)

## 2. Convenciones detectadas en los proyectos de referencia

- **Maven multi-módulo**: `pom.xml` raíz declara `<modules>` — típicamente `all, core, ui.frontend?, ui.apps, ui.apps.structure, ui.config, ui.content, it.tests, ui.tests`. `ui.frontend` es opcional (Repsol-Lubricantes no lo tiene → sus componentes usan clientlibs "clásicos" con CSS/JS directos en `ui.apps`, sin webpack).
- **Perfiles Maven estándar** encontrados en el pom raíz: `autoInstallBundle` (solo el bundle OSGi, rápido), `autoInstallPackage` (paquete de contenido completo), `autoInstallPackagePublish`, y compilación simple sin perfil (`mvn clean install`, sin desplegar a ninguna instancia).
- **`ui.frontend/package.json`** típico trae scripts `dev`, `prod`, `start` (webpack-dev-server), `watch` (`npm-run-all --parallel start chokidar aemsyncro`), `sync`/`aemsyncro` (vía `aemsync`) y a veces un script `push` que llama a una CLI de vault (`vlt`/`filevault-content-package-maven-plugin` o similar) contra una ruta de clientlib concreta. **Compilar "solo front"** = correr estos scripts npm dentro de `ui.frontend` sin pasar por el reactor Maven completo; **"solo back"** = `mvn clean install -pl '!ui.frontend'` (o `-pl core,ui.apps,...`) para no disparar el build de webpack.
- **Componentes** viven en `ui.apps/src/main/content/jcr_root/apps/<namespace>/components/<nombre>[/v1|v2]/<nombre>`, con `_cq_dialog`, `_cq_design_dialog` y a veces `_cq_template`/`new` (versión inicial "in construction"). El versionado (`v1`, `v2`…) es una convención propia del proyecto, no del arquetipo — la extensión debe **preguntar** si se versiona o no.
- **Modelos Sling** en `core/src/main/java/com/<empresa>/<proyecto>/core/models/<nombre>[/v1]/`, con subcarpetas por versión igual que el componente. `Cart.java` (gatesconnect-aem) es el ejemplo de modelo que expone datos a un componente React vía un `HashMap`/mapper para hidratar el estado inicial del bundle JS — patrón a replicar en el bloque 18.
- **`components/utils`** (ej. `gatesconnect-aem/ui.apps/.../apps/gatesconnect/components/utils`) es donde viven los `data-sly-template` compartidos entre componentes.
- **i18n**: diccionarios como nodos `sling:MessageEntry` bajo `i18n/<idioma>` en `ui.content` (o `ui.apps`), una entrada por `sling:key`/`sling:message`.

## 3. Detalle de las funcionalidades y decisiones de UX

### 3.1 Compilar proyecto (Bloque 1)
Panel **anclado en la propia barra de actividad de la extensión** (una vista más, debajo de "Acciones" — no una pestaña de editor aparte ni una cadena de QuickPicks), al estilo de una configuración de ejecución de IntelliJ: un **select de Modo** arriba y, debajo, los **perfiles Maven como checkboxes** (se pueden marcar varios a la vez, ej. `autoInstallBundle` + `autoInstallPackage` juntos — algo que un único QuickPick no permitía bien). Al ejecutar "AEM: Compilar proyecto...", la vista se enfoca sola en la barra lateral y (re)elige el proyecto si hay varios abiertos; si el panel aún no se había abierto nunca, muestra primero un estado vacío con un botón "Elegir proyecto" (para no disparar el selector de proyecto sin que el usuario lo pida).

Modos disponibles:
1. **Completa**: front + back + tests (de back, y de front si el proyecto tiene un script de test en `ui.frontend/package.json`). Corre el reactor Maven completo y, si aplica, los tests de front después. Es el modo que carga por defecto al abrir el panel.
2. **Solo Front**: corre `aemToolkit.frontBuildCommand` (por defecto `npm run dev`, sin Maven). Si hay script de test de front, se puede saltar con un checkbox.
3. **Solo Back**: al elegir este modo se **desmarcan todos los checkboxes y se marcan automáticamente `autoInstallBundle` y `autoInstallPackage`** (los que existan en el proyecto). Corre con tests incluidos por defecto; el usuario puede desmarcar "Saltar tests de Back" para incluirlos, o marcarlo para saltarlos.
4. **Test-coverage Frontend**: solo aparece habilitado si `ui.frontend/package.json` tiene un script de coverage (ej. uno que corra con `--coverage`). Lo corre y muestra el reporte (ver abajo).
5. **Test-coverage Backend**: usa `git status --porcelain` para detectar si hubo cambios en el back desde el último commit guardado. Si los hay, compila todo el back + tests; si no, solo re-corre los tests (para no perder tiempo recompilando). Si el proyecto no tiene `jacoco-maven-plugin` configurado, se ofrece agregarlo automáticamente como un perfil `coverage` en el pom raíz (heredado por todos los módulos, igual que `autoInstallBundle`/`Package`) — y ese perfil `coverage`, una vez existe, se marca solo al elegir este modo. Al terminar, se muestra un panel con el **% de coverage de líneas por clase**, con buscador por nombre y un filtro "mostrar coverage menor a X%" para ubicar rápido los modelos con poca cobertura. Los tests no se pueden saltar en este modo (son necesarios para calcular coverage).
6. El usuario puede **guardar el estado actual del panel como un modo personalizado con nombre** (perfiles marcados, skip tests de front/back, destino Author/Publish, argumentos extra) — aparece después en el mismo select, bajo "Modos personalizados", y se puede eliminar con el ícono 🗑.

**Perfiles y demás valores por defecto según el modo**: cada modo base trae asociados los perfiles que normalmente necesita para instalar (Completa y Solo Back → `autoInstallBundle`+`autoInstallPackage` si existen; Test-coverage Backend → `coverage` si ya existe) y los marca automáticamente al elegirlo — **incluyendo el modo "Completa" que carga por defecto al abrir el panel** (antes esto solo pasaba en "Solo Back"). Al cambiar de modo también se reinician a su valor por defecto los checks de "saltar tests" (front/back, sin saltar), el campo de argumentos extra (vacío) y el destino de despliegue ("No aplica"), para que nunca quede un valor de un modo anterior "pegado" en la UI. Los modos personalizados guardados no se ven afectados por este reinicio: siguen cargando exactamente los valores con los que se guardaron.

Para los modos que instalan en una instancia (Completa/Solo Back), se muestra además el **destino Author (puerto `4502`) / Publish (puerto `4503`) / No aplica**, con host/puerto precargados con esos estándares (ver perfil hermano `<perfil>Publish`, igual que antes). La detección de perfiles lee tanto el `pom.xml` raíz como los `pom.xml` de los submódulos de primer nivel (ej. `fedDev`, definido dentro de `ui.frontend/pom.xml` en gatesconnect-aem), para que ningún perfil "escondido" en un submódulo se quede fuera de la lista.

La ejecución corre como una **VS Code Task** (no un simple `sendText` a una terminal) — el usuario sigue viendo el output real en un panel de terminal, pero esto permite encadenar pasos (ej. build → tests) y saber si terminó bien antes de continuar (ej. antes de leer el reporte de coverage).

**Acciones rápidas (estilo ventana "Maven" de IntelliJ)**: arriba del select de Modo hay una fila de íconos para operaciones puntuales de Maven que no dependen del wizard de Modo/perfiles, igual que la barra de herramientas del panel Maven de IntelliJ:
- 📥 Descargar dependencias (`mvn dependency:resolve`).
- 🗂️ Generar sources y actualizar carpetas (`mvn generate-sources`).
- ▶ Compilar con los perfiles marcados abajo — **reactor completo, incluye `ui.frontend`** —, con tests (`mvn clean install`). Es el equivalente al ícono "ejecutar perfiles marcados" del panel Maven de referencia.
- ⚡ Compilar con los perfiles marcados abajo — reactor completo —, saltando los tests tanto de back como de front (`mvn clean install -DskipTests`). Es el equivalente al ícono "ejecutar perfiles marcados sin tests" (▶/⊘) del panel Maven de referencia.
- 🧹 Limpiar (`mvn clean`).
- 🌳 Ver árbol de dependencias (`mvn dependency:tree`).
- 🔍 Analizar dependencias — declaradas sin usar / usadas sin declarar (`mvn dependency:analyze`), igual que "Analyze Dependencies" en IntelliJ.

Todas usan los perfiles que estén marcados en ese momento en la sección "Perfiles Maven" (no el modo elegido en el select). Descargar dependencias, generar sources, limpiar, árbol y análisis de dependencias excluyen `ui.frontend` del reactor (`-pl !ui.frontend -am`), igual que "Solo Back", para no disparar de rebote un build de webpack al pedir algo puramente de Maven — las excepciones son ▶ Compilar y ⚡ Compilar sin tests, que sí incluyen `ui.frontend` a propósito (ver arriba).

**Detener una compilación en curso**: mientras hay una Task de Maven/npm corriendo (lanzada desde ▶, ⚡, cualquier acción rápida, o el botón "▶ Compilar" del wizard de Modo), el ícono ▶ se transforma en un **recuadro rojo ⏹** — al pulsarlo, se llama a `TaskExecution.terminate()` sobre la Task en curso. Mientras tanto, el resto de los botones del panel quedan deshabilitados (no se pueden lanzar dos compilaciones en paralelo sobre el mismo reactor). Al terminar — bien, con error, o detenida manualmente — el ícono vuelve a ▶ y todo se re-habilita solo. Cuando se detiene manualmente, el mensaje final lo dice explícitamente ("⏹ ... detenida por el usuario.") en vez de mostrarlo como un error con código `undefined` (que es lo que reporta VS Code cuando una Task se termina a la fuerza en vez de salir sola).

**JDK usado al compilar — v1.1.2/1.1.3, con detección automática desde v1.2.0**: todas las Tasks de Maven que lanza el panel (▶, ⚡, y las acciones rápidas) corren en la shell integrada de VS Code (bash/Git Bash, cmd, etc.), que resuelve su propio `JAVA_HOME`/PATH — **no necesariamente el mismo JDK que un IDE como IntelliJ**, que permite fijar el JDK del proyecto de forma independiente al PATH del sistema. Si son distintos, un plugin de Maven compilado para una versión de Java más nueva que la que trae esa shell por defecto falla con `UnsupportedClassVersionError` aunque el comando `mvn` ejecutado sea idéntico al de IntelliJ.

Flujo completo (`src/compile/javaResolver.ts`):
1. **Versión requerida**: se lee de `maven.compiler.release`/`target`/`source` o `java.version` en el pom raíz y en el de cada módulo (la más alta encontrada) — queda en `AemProjectInfo.requiredJavaVersion`.
2. **Versión del sistema**: se detecta corriendo `java -version` (respetando `JAVA_HOME` si está seteado), sin ninguna configuración de la extensión de por medio.
3. Si **`aemToolkit.javaHome`** está configurado a mano, gana siempre — no se hace ninguna detección ni se pregunta nada.
4. Si no, y la versión requerida coincide con la del sistema, tampoco pasa nada — se usa el JDK del sistema tal cual.
5. Si no coinciden, se busca en **`aemToolkit.jdkSearchFolders`** (máx. 2, carpetas "contenedoras" de varios JDKs, ej. `C:\Program Files\Java` con subcarpetas `jdk-11`, `jdk-17`...) una instalación cuya versión coincida — por su archivo `release` (JDK 9+, sin lanzar procesos), el nombre de la carpeta, o como último recurso ejecutando su propio `java -version`. Si encuentra una, la usa automáticamente (antepone su `bin` al `PATH` y fija `JAVA_HOME` solo para esa Task) sin preguntar nada.
6. Si tampoco se encuentra ninguna que coincida, el panel muestra un **banner de aviso** arriba ("⚠ El proyecto requiere Java X pero el sistema tiene Java Y...") y, al intentar compilar, se pregunta *"¿Deseas continuar de todas formas?"* con la opción de abrir la configuración ahí mismo.

**Ícono ⚙️** en la barra de acciones rápidas: abre un menú (detectar de nuevo, configurar las carpetas de búsqueda, configurar el JDK a mano, o abrir la configuración completa de la extensión). `aemToolkit.javaHome` y `aemToolkit.jdkSearchFolders` son configuraciones de **workspace** (`"scope": "resource"`): cada proyecto fija lo suyo (o nada) sin afectar a los demás.

### 3.2 Subir cambios de front sin compilar (Bloque 2) — ✅ v1.1.0, sincronización de `.content.xml` corregida de fondo en v1.3.0
Sincroniza archivos directo al JCR sin pasar por Maven ni webpack, usando la **API POST de Sling** directamente contra Author o Publish.

- **Disparador**: clic derecho sobre un archivo o carpeta dentro de `ui.apps/.../jcr_root/...` (menú `explorer/context` y `editor/context`, visible solo cuando la ruta contiene `jcr_root`) → **"AEM: Subir a Author"** o **"AEM: Subir a Publish"**. Si es un archivo, sube solo ese archivo; si es una carpeta, recorre recursivamente todo su contenido y sube cada archivo encontrado.
- **Ruta JCR real**: se calcula a partir de la ruta local recortando todo lo anterior a `jcr_root` y decodificando la convención "platform" de FileVault (`_cq_dialog` → `cq:dialog`, `_jcr_content` → `jcr:content`) en cada segmento.
- **Archivos `.content.xml` (`src/sync/docview.ts` + `src/sync/contentXmlSync.ts`) — reescrito en v1.3.0**: hasta la v1.2.0 se subían con `:operation=import`/`:contentType=xml` del Sling POST Servlet, que resultó ser **el bug real**: ese `contentType` no entiende el formato Document View de FileVault (heredado en cambio del bundle `jcr.contentloader`, con un esquema `<node><name>.../<name></node>` totalmente distinto) — la petición daba HTTP 200 pero no aplicaba los cambios. Ahora el `.content.xml` se interpreta localmente con `fast-xml-parser` (nodo por nodo, con tipos `{Boolean}`/`{Long}`/etc. y arreglos `[a,b,c]` vía `parseDocView`/`parseDocViewValue`) y se reconstruye la subida como una serie de POSTs normales de Sling (uno por nodo, con `jcr:primaryType` y cada propiedad como campos de formulario + `@TypeHint`), vía `pushNodeTree`. Dos comportamientos distintos según el archivo:
  - **Diálogo de edición (`_cq_dialog/.content.xml` — incluye tanto el diálogo de un componente normal como el de "propiedades de página", que usa el mismo mecanismo bajo el componente de página/plantilla)**: reemplazo total. Se borra el nodo completo en el servidor (`:operation=delete`, ignorando 404/410 — nada que borrar la primera vez) y se recrea desde cero con `pushNodeTree`, así que tanto los cambios como los campos eliminados del archivo quedan reflejados en AEM.
  - **Cualquier otro `.content.xml`**: solo se crean/actualizan nodos y propiedades — nunca se borra nada en el servidor. Para avisar si el usuario eliminó algo (sin consultar el servidor AEM en absoluto, por decisión explícita): se compara el árbol actual contra la última versión commiteada en git (`git show HEAD:<ruta>`, vía `detectLocalDeletions`); si esa versión anterior tenía una propiedad o nodo que ya no está, se sincroniza igual lo demás y se avisa que hay que correr una compilación completa para aplicar la eliminación. Si el archivo no está en git todavía, no se avisa nada (no hay con qué comparar).
- **Cualquier otro archivo** (HTML, CSS, JS, imágenes...): se sube como `nt:file` con la técnica estándar de la Sling POST Servlet — campo de formulario `*` (toma el nombre del nodo del archivo subido) + `*@TypeHint=nt:file`, contra el nodo padre.
- Requiere que el nodo padre ya exista en el servidor (pensado para actualizar algo ya instalado antes con una compilación completa, no para crear estructura nueva desde cero).
- **Progreso y cancelación**: barra de progreso con notificación (`vscode.window.withProgress`, cancelable) mientras sincroniza varios archivos; un canal de salida "AEM Toolkit — Sync" registra cada archivo (✔/✘) para revisar errores puntuales sin perder el resto de la sincronización.
- **Credenciales**: host/puerto de Author y Publish son configuración normal (`aemToolkit.sync.*`, con los estándares `4502`/`4503`/`admin` precargados); la(s) contraseña(s) se configuran aparte con **"AEM: Configurar credenciales de sincronización..."** (también disponible en el árbol, bajo "Sincronizar") y se guardan en VS Code Secret Storage, nunca en `settings.json`. Si nunca se configuró una contraseña, se usa `admin` (estándar de una instancia AEM local recién instalada).
- **Dependencia nueva (v1.3.0)**: `fast-xml-parser` (+ `strnum`, su única dependencia) para interpretar el Document View XML — ambas empaquetadas en el `.vsix` (excepción explícita en `.vscodeignore`, que por defecto excluye todo `node_modules/**`).
- Verificado con un servidor Sling simulado (dentro del mismo proceso de Node, sin red real) contra el `.content.xml` real de `eventosgrid/_cq_dialog` del proyecto `italika-v2-cloud`: la secuencia de POSTs generada, el orden padre-antes-que-hijo, y los campos/tipos de cada propiedad se revisaron a mano — pero no se pudo probar contra una instancia AEM real desde este entorno (sin red hacia `localhost` del usuario), así que la primera sincronización de un diálogo real conviene probarla en un componente de prueba antes de confiar en el borrado.

### 3.3 Crear componente (Bloque 17) — 🟡 primera iteración construida en v2.1.0, ajustes en v2.1.1–v2.1.11

**Primera iteración (esta entrega)**: estructura del componente + diálogo vacío + clientlib de estilos/JS, consciente de `ui.frontend`. **El modelo Sling (con modelo / solo HTL estático) queda para una iteración siguiente** — a pedido explícito, para no inflar el primer formulario — y el componente React/Angular (Bloque 18) sigue dependiendo de que el 17 esté terminado, como ya indica la tabla del punto 1.

**Disparador y menú** (ajustado en v2.1.2, a pedido explícito): clic derecho sobre **cualquier carpeta dentro de `ui.apps`** (`explorerResourceIsFolder` + `resourcePath` contiene `jcr_root` y `ui.apps` — condición deliberadamente amplia, sin exigir que sea justo `components`) → submenú **"Crear nuevo..."** (`aemToolkit.createMenu`, anidado dentro del submenú "AEM Toolkit" ya existente, vía `contributes.submenus` — VS Code permite anidar un `submenu` dentro de otro) → **"Componente"**. Este submenú nace pensado para los próximos "crear nuevo X" del roadmap (tags/Bloque 3, Content Fragment Model/Bloque 5, template de página/Bloque 10…), que se irán agregando como nuevas entradas sin tener que reestructurar el menú de nuevo.

La condición `when` de VS Code solo puede evaluar el texto de la ruta/nombre del recurso — no puede leer el disco para saber si esa carpeta ya es un componente, así que ese chequeo se hace en tiempo de ejecución dentro del propio comando: si la carpeta sobre la que se hizo clic ya tiene su propio `.content.xml` (o sea, ya es un componente — proxy, versión real, o componente sin versión), no se abre el formulario. A partir de ahí hay dos casos, distinguidos con `isAlreadyVersionedComponent` (`componentVariant.ts`: ¿tiene alguna subcarpeta `vN` con su propio `.content.xml`?), y **ambos se resuelven directo, sin formulario** (desde v2.1.11 — antes el caso ya-versionado solo avisaba y redirigía):
- **Ya es un componente versionado (proxy)**: se ofrece crear directamente la siguiente versión (`vN+1`). Ver más abajo, "Crear la siguiente versión de un componente ya versionado".
- **Es un componente real SIN versionar todavía**: se ofrece convertirlo en una **variante** versionada. Ver más abajo, "Convertir un componente sin versionar en variante".

**Paso 0 — detección del proyecto** (antes de abrir el formulario, usando `AemProjectInfo` ya existente en `projectDetector.ts`):
- `hasFrontendModule` decide si el formulario ofrece el switch "Añadir al módulo frontend" (ver más abajo).
- **Preprocesador dominante**: se detecta mirando qué extensión usan los componentes ya existentes (`.scss`/`.less`/`.css` en `ui.frontend/src/main/webpack/components/**` si hay frontend, o en los `css.txt` de clientlibs clásicos si no). Si el proyecto usa **una sola** extensión de forma consistente, esa queda precargada por defecto en el selector (el usuario la puede cambiar igual). Si el proyecto **combina extensiones** (ej. algunos componentes en `.css` y otros en `.scss`, o `.css` mezclado con `.less`), no se asume ninguna: el selector queda **sin valor por defecto** y se le pide explícitamente al usuario que elija con cuál de las extensiones detectadas en el proyecto quiere este componente nuevo.
- **Convención de nombres**: se mira si los componentes existentes usan kebab-case o camelCase, para validar el nombre nuevo contra esa misma convención además de contra los caracteres válidos de un nombre de nodo JCR.
- **Grupos de componentes existentes** (`componentGroup` de los `.content.xml` ya creados) para ofrecerlos como autocompletado y evitar grupos duplicados por typo.

**Formulario (Webview, mismo patrón que el editor de diálogos)**:
1. **Nombre** del componente — valida en vivo contra la convención detectada y contra nombres de nodo JCR válidos; muestra la ruta resultante en tiempo real (ver punto 2).
2. **Título** (`jcr:title`) — precargado a partir del nombre (capitalizado/espaciado), editable.
3. **Grupo de componentes** (`componentGroup`) — combo con autocompletado sobre los grupos detectados, permite escribir uno nuevo.
4. **Versionado** — switch, **"normal" por defecto**. Al activarlo: si no existe ningún componente con ese nombre, crea `v1`; si ya existe (sin versión, o con versiones previas), crea la siguiente (`v2`, `v3`…). Si el switch de versionado no coincide con el esquema del componente ya existente con ese nombre (ej. ya existe sin versión y ahora se pide versionado, o viceversa), **no se resuelve solo**: se avisa al usuario y se pregunta cómo seguir, en vez de mezclar ambos esquemas en silencio.
   - **Esquema de versionado confirmado — patrón "proxy" estándar de Adobe**: `components/<nombre>` es un componente **proxy sin versión** (`.content.xml` mínimo, solo con `sling:resourceSuperType` apuntando a la versión vigente); la implementación real de cada versión vive en `components/<nombre>/v1`, `components/<nombre>/v2`… (sin repetir el nombre adentro). El `resourceType` que se usa en páginas/plantillas es siempre el del proxy (`.../components/<nombre>`) y **no cambia** al pasar de v1 a v2 — al crear una versión nueva, la extensión actualiza el `sling:resourceSuperType` del proxy para que apunte a la última. Si el componente **no** es versionado, no hay proxy: `components/<nombre>` es directamente el componente real.
5. **Generar hoja de estilos** — switch, **activado por defecto** (según `aemToolkit.componentsCreateCssJsByDefault`); si está activo, selector de preprocesador (CSS/SCSS/LESS). **Valor por defecto según el modo (ajustado en v2.1.6, a pedido explícito)**: con `ui.frontend` se respeta la extensión dominante/detectada del proyecto en el Paso 0 (ya usa un preprocesador vía webpack, tiene sentido seguir su convención); con clientlib clásica se precarga **CSS** en vez de eso (sin paso de compilación en `ui.apps`, CSS es la opción segura por defecto) — en ambos casos el usuario puede cambiarlo con el selector, y a partir de ahí deja de recalcularse solo al cambiar de modo. El archivo generado arranca con la **clase raíz en BEM** `.<nombre-del-componente>-cmp` (ej. componente `hello-word` → `.hello-word-cmp`), lista para anidar elementos/modificadores BEM (`&__elemento`, `&--modificador` en SCSS/LESS; clases planas `.hello-word-cmp__elemento` en CSS puro). Esa misma clase se agrega como `class` del elemento raíz del `.html` generado, para que el selector aplique sin que el usuario tenga que conectarlo a mano.
6. **Generar JS** — switch, **activado por defecto** (misma configuración).
7. **Añadir al módulo frontend** — switch, **solo visible si `hasFrontendModule` es true Y (estilos o JS están activos)**, **activado por defecto**. Si se desactiva (o si no hay `ui.frontend`), se crea una clientlib clásica propia del componente en `ui.apps` en su lugar.
7bis. **Carpeta base donde se generan los estilos/JS** (agregado en v2.1.3, a pedido explícito) — campo de texto + botón "📁 Elegir..." (abre el selector nativo de carpetas de VS Code, `vscode.window.showOpenDialog`), visible junto con el switch anterior en cuanto estilos o JS están activos. Se precarga sola con la ruta por defecto correspondiente (`ui.frontend/src/main/webpack/components/<nombre>` si se usa el módulo frontend, o `apps/<namespace>/clientlibs/clientlib-components/<nombre>` si es una clientlib clásica — convención ajustada en v2.1.4, ver más abajo) y **se recalcula en vivo** cada vez que cambia el nombre, la versión, o el switch "Añadir al módulo frontend" — pero deja de recalcularse en cuanto el usuario la edita a mano o elige una carpeta distinta con el botón, para no pisarle una elección explícita. La función que calcula el valor por defecto (`computeDefaultAssetsDir`) es la misma que usa la creación real, para que la vista previa nunca quede desincronizada de dónde se escribe de verdad.
   - **Vista previa de las 2 rutas resultantes (agregado en v2.1.5, a pedido explícito)** — debajo del campo aparecen, solo si aplica, "📄 CSS: ..." y "📄 JS: ..." con la ruta final exacta de cada uno (cada línea visible únicamente si su switch correspondiente — "Generar hoja de estilos" / "Generar JS" — está activo), para que el usuario tenga contexto claro de dónde termina cada tipo de archivo **aunque ambas coincidan** (caso `ui.frontend`, donde CSS y JS van a la misma carpeta). Se recalculan en vivo con cada cambio a la carpeta base (a mano, por "Elegir...", o por el recálculo automático del punto anterior) vía el mensaje `computeAssetPaths`, resuelto con la misma función (`computeAssetSubPaths`) que usa la creación real.
8. **Opciones avanzadas** (sección plegable, igual que el editor de diálogos oculta el detalle de cada campo hasta que se pulsa "Editar"):
   - `_cq_editConfig.xml` (`cq:EditConfig` + `cq:listeners` con `afteredit`/`afterinsert`/`afterdelete`/`aftermove="REFRESH_PAGE"`) — **activado por defecto** (sin esto, el autor tiene que refrescar la página a mano tras cada edición del diálogo; es la sorpresa más común para quien no lo conoce).
   - `_cq_design_dialog/.content.xml` — desactivado por defecto.
   - `_cq_template/.content.xml` (contenido inicial al arrastrar el componente "nuevo" a una página) — desactivado por defecto.
   - Placeholder de "componente sin configurar" en el HTL (`data-sly-test` mostrando un aviso mientras no haya contenido) — activado por defecto. **Texto mostrado al autor** (confirmado en v2.1.6): el patrón `cq-placeholder` de AEM (`data-emptytext="<Título>"`) — en modo edición del Page Editor, mientras el componente no tenga contenido, se ve un recuadro punteado con el **título** del componente tal cual se escribió en el formulario (ej. "Hero Banner"), igual que hacen los Core Components de Adobe cuando están vacíos; en publicación/preview no se ve nada (`wcmmode.edit` lo oculta). En v2.1.6 también se reordenó el bloque generado, a pedido explícito, para que el `<div class="cq-placeholder"...>` quede **entre** los dos comentarios TODO (antes quedaba encima de ambos): primero "TODO: contenido del componente", después el bloque del placeholder, y por último "TODO: reemplaza este placeholder por una condición real una vez el diálogo tenga campos".
   - **Abrir hoja de estilos + HTML + diálogo apenas se crea el componente** (ampliado en v2.1.7, a pedido explícito — antes solo abría el diálogo) — activado por defecto, para encadenar directo con la edición. Abre, en este orden, como pestañas normales: la hoja de estilos (si se generó — el CSS/JS de la clientlib clásica, o el parcial de `ui.frontend` según el modo), el `.html` del componente, el `_cq_dialog/.content.xml` recién creado como texto plano, y por último ese mismo diálogo en el editor visual (Bloque 19/20) — el editor visual queda como pestaña activa al terminar, por ser lo más probable que el usuario quiera seguir editando ahí, pero el XML queda igual disponible como pestaña (ver v2.1.8 más abajo). El JS no se abre automáticamente (no fue parte del pedido). Si se desactiva este switch, no se abre nada solo.

**Clientlib — mecánica según `ui.frontend`**:
- **Con `ui.frontend` activo**: el JS y los estilos se generan en la carpeta elegida por el usuario (por defecto `ui.frontend/src/main/webpack/components/<nombre>` — ver punto 7bis). **No alcanza con crear los archivos sueltos**: hay que registrar el nuevo parcial en el punto de entrada que webpack ya compila (ej. agregar `@import` al `main.scss`/`.less` y el `import`/`require` correspondiente al entry JS) — se detecta leyendo la estructura real de `ui.frontend/src/main/webpack` del proyecto, sin asumir un nombre de archivo índice fijo, para no dejar el componente nuevo huérfano de compilación. La ruta de import se calcula siempre relativa entre el archivo agregador/entrypoint encontrado y la carpeta real elegida (`path.relative`, nunca una convención fija `components/<nombre>/...`), para que siga funcionando aunque el usuario haya elegido una carpeta fuera de la convención habitual. **El HTL del componente NO embebe ninguna categoría de clientlib en este modo** (fix v2.1.3: antes se agregaba igual un `data-sly-call` a una categoría que nunca se creaba) — en su lugar deja un comentario explicando que los estilos/JS se compilan junto con el resto del sitio vía webpack.
- **Sin `ui.frontend` (o switch "Añadir al módulo frontend" desactivado)**: se crea una `clientlib` clásica propia del componente en la carpeta elegida por el usuario (por defecto `apps/<namespace>/clientlibs/clientlib-components/<nombre>` — ver punto 7bis), con `.content.xml` de tipo `cq:ClientLibraryFolder`, `categories` con la convención `<namespace>.<nombre>`, y sus `css.txt`/`js.txt` + archivos. El HTL generado la embebe **inline dentro del propio componente** con el patrón de AEM Core Components (`data-sly-use.clientlib="core/wcm/components/commons/v1/templates/clientlib.html"` + `data-sly-call="${clientlib.css @ categories='<namespace>.<nombre>'}"`/`.js`) — confirmado como el patrón que siguen los proyectos de referencia, y solo se agrega cuando esta clientlib realmente se crea.
  - **Ubicación ajustada en v2.1.4, a pedido explícito** (antes se anidaba dentro de la propia carpeta del componente, ej. `components/app-banner/clientlibs/app-banner`, lo que no seguía la convención habitual de los proyectos de referencia): ahora vive a nivel del namespace, hermana de `components`, dentro de una carpeta contenedora `clientlibs/clientlib-components/` que agrupa las clientlibs de todos los componentes clásicos del proyecto. Esa carpeta contenedora **no tiene su propio `.content.xml`** (no es en sí misma una clientlib, solo agrupa) — se crea automáticamente al escribir el primer archivo dentro (`fs.mkdirSync(..., {recursive:true})`) sin ningún paso extra. Cada componente conserva su **propia subcarpeta-clientlib independiente**, con su propio `.content.xml`/categoría (`<namespace>.<nombre>`) — no es una clientlib única compartida por todos los componentes, para no forzar que todos los estilos se carguen siempre juntos en cada página. Un componente versionado usa **una sola clientlib compartida entre sus versiones** (misma categoría, no una por versión), consistente con que solo una versión está activa a la vez a través del proxy. La detección de extensión de estilos dominante/mixta (Paso 0) fue ajustada para seguir escaneando también esta carpeta compartida.
  - **CSS y JS en su propia subcarpeta dentro de la clientlib (agregado en v2.1.5, a pedido explícito)**: el archivo de estilos ya no queda suelto junto al `.content.xml` de la clientlib — vive en `<clientlib>/css/<nombre>.<ext>`, referenciado desde `css.txt` con `#base=css`; el JS vive igual en `<clientlib>/js/<nombre>.js`, referenciado desde `js.txt` con `#base=js`. Así la raíz de la clientlib no se aglomera si el usuario necesita agregar más ficheros de estilos o JS más adelante (parciales, utilidades, etc.) — cada tipo tiene su propio espacio. **No aplica a `ui.frontend`**: ahí CSS y JS siguen yendo juntos en la misma carpeta del componente dentro de `ui.frontend/src/main/webpack/components/<nombre>` (es la convención webpack ya existente del proyecto, no una clientlib, y no tiene el mismo problema de aglomeración).
  - **No se sobreescribe un CSS/JS ya existente (agregado en v2.1.7, a pedido explícito)**: antes de escribir el archivo de estilos o el JS, la extensión valida si ya existe uno en esa ruta exacta — típicamente porque la clientlib es la misma compartida entre versiones de un componente versionado (ver más arriba: una sola clientlib para todas las versiones), y esa clientlib ya fue personalizada a mano tras crear una versión anterior. Si ya existe, se preserva tal cual (no se pisa con el contenido de arranque) y se avisa en el mensaje de confirmación. Los metadatos de la clientlib (`.content.xml`, `css.txt`, `js.txt`) sí se regeneran siempre, porque son declarativos y necesitan reflejar el switch de estilos/JS vigente (ej. si una versión nueva agrega JS a una clientlib que antes solo tenía CSS) — solo el código fuente real de CSS/JS se protege. La misma protección aplica también en modo `ui.frontend`, por si se re-genera sobre una carpeta ya usada.

**Archivos que genera esta primera iteración**: `.content.xml` del componente (`cq:Component`, `jcr:title`, `componentGroup` — sin `sling:resourceType` propio, porque el resourceType de un componente lo define su propia ruta bajo `/apps`, no una propiedad suya; el proxy de un versionado en cambio sí lleva `sling:resourceSuperType` apuntando a la versión vigente), `.html` (con el placeholder opcional y el embed de clientlib si aplica), `_cq_dialog/.content.xml` (vacío, listo para abrirse en el editor visual), y — según las opciones avanzadas marcadas — `_cq_editConfig.xml`, `_cq_design_dialog/.content.xml`, `_cq_template/.content.xml`, y la clientlib clásica si corresponde. **Todos estos `.xml` se reformatean antes de escribirse (agregado en v2.1.9, a pedido explícito)** con el mismo estilo que usa "AEM: Formatear XML" (`reformatXml`, compartida desde `docviewSerializer.ts` — no es lógica nueva, se reusa la existente) en vez de quedar con el string literal crudo de cada plantilla; si algún archivo no fuera XML de Document View válido por algún motivo, se deja tal cual en vez de romper la creación del componente.

**Construido en v2.1.0** (`src/component/componentDetector.ts`, `componentTemplates.ts`, `componentGenerator.ts`, `componentPanel.ts`, `componentCreate.ts`): disparador "Crear nuevo... → Componente" (clic derecho sobre `components` o una subcarpeta suya, dentro de `jcr_root`), formulario Webview con vista previa de ruta en vivo y bloqueo de creación si el esquema de versionado no coincide con un componente ya existente del mismo nombre, esquema de versionado "proxy" verificado con el usuario (`components/<nombre>` = proxy sin versión con `sling:resourceSuperType` hacia la última versión; `components/<nombre>/v1`, `v2`... = implementación real; el proxy se reescribe para apuntar a la versión nueva cada vez que se agrega una), detección de extensión de estilos dominante o mixta, detección de convención de nombres y de `componentGroup`s existentes, y el intento de registro automático en el entrypoint de webpack (`registerWebpackEntry`, con aviso explícito si no encuentra un archivo agregador/entrypoint reconocible, en vez de fallar en silencio). Probado con un proyecto AEM simulado (sin red real, igual que el resto de la extensión) cubriendo: versionado consecutivo (v1→v2→v3, proxy actualizado en cada paso), clientlib clásica sin `ui.frontend`, y detección de mezcla de extensiones de estilos — pero, igual que el sync de `.content.xml` (ver 3.2), no se pudo probar contra una instancia AEM real ni contra un `ui.frontend`/webpack real desde este entorno, así que conviene probar el primer componente creado en un proyecto de prueba antes de confiar en el registro automático del entrypoint de webpack. **Pendiente para la siguiente iteración**: modelo Sling (con/sin modelo), y el componente React/Angular del Bloque 18 (que depende de este).

**Convertir un componente sin versionar en variante (agregado en v2.1.10, a pedido explícito)** — módulo nuevo `src/component/componentVariant.ts`: al hacer clic derecho con "Crear componente" directamente sobre la carpeta de un componente **ya existente pero sin versionar** (tiene su propio `.content.xml` con el contenido real directo adentro — `.html`, `_cq_dialog`, clientlib propia si la tuviera — y ninguna subcarpeta `v1`/`v2`), en vez de mostrar solo un aviso se pregunta con un modal ("¿Deseas crear una variante (versión nueva)?", `showWarningMessage` con `{modal:true}` y el botón "Crear variante") si se quiere convertir al esquema versionado. Si el usuario confirma, `migrateComponentToVariant` hace lo siguiente:
1. **Todo el contenido actual de la carpeta se mueve tal cual a `v1/`** (`fs.renameSync` por cada entrada existente) — nada se reescribe: cualquier propiedad propia del `.content.xml` original (icono, `allowedParents`, cualquier `sling:resourceSuperType` previo de una herencia real distinta, etc.), y cualquier archivo/subcarpeta adicional (clientlib propia incluida) quedan intactos dentro de `v1`.
2. **La carpeta pasa a ser el proxy**: se reusa el `.content.xml` **original** (leído antes de mover nada) como base — se preservan tal cual todas sus propiedades propias (título, grupo, ícono, `allowedParents`...), porque son las que definen cómo se ve/comporta el componente para el autor y porque el proxy es la ruta que de verdad se referencia desde páginas/plantillas — y se le agrega/sobreescribe únicamente `sling:resourceSuperType` (sin tocar el resto de propiedades).
3. **`v1` se duplica tal cual para crear `v2`** (copia recursiva de archivos), como punto de partida de la variante nueva — el usuario ajusta luego `v2` a mano (HTL, diálogo, clientlib...) para que sea la variante real. El proxy queda apuntando a `v2` (la más nueva), consistente con el resto de la extensión (mismo criterio que al agregar una versión nueva desde el formulario).

Tras la migración se muestra un mensaje de confirmación indicando qué carpeta es `v1` (contenido original) y cuál `v2` (ruta relativa al proyecto, variante nueva a ajustar), y se auto-abren el `.html` y el diálogo de **`v2`** (mismo criterio de auto-apertura que al crear un componente desde cero — ver punto 8 más arriba y 3.10 —, usando la misma `openDialogEditor` compartida) si existen, para encadenar directo con la edición de la variante. Si la carpeta ya es un componente versionado (proxy con subcarpetas `vN`), en cambio se ofrece crear la siguiente versión directamente — ver el punto siguiente — ambos casos comparten el mismo punto de entrada, distinguidos por `isAlreadyVersionedComponent`. Verificado con un componente simulado con propiedades JCR extra (`cq:icon`, `allowedParents`) confirmando que sobreviven intactas tanto en `v1` como en el proxy final, que `v2` es un duplicado exacto de `v1`, y que el proxy termina apuntando a `.../v2` (no a `v1`).

**Crear la siguiente versión de un componente ya versionado (agregado en v2.1.11, a pedido explícito — cierra un pendiente que había quedado abierto en v2.1.10)**: al hacer clic derecho con "Crear componente" directamente sobre la carpeta de un componente **ya versionado** (proxy con al menos una subcarpeta `vN` con su propio `.content.xml`), la extensión ya no se limita a avisar y redirigir al formulario — resuelve directo, igual que el caso de la variante: un modal pregunta "¿Deseas crear 'vN+1' a partir de 'vN'?" (mostrando los números reales, ej. "v3" a partir de "v2") con el botón "Crear versión". Si se confirma, `createNextVersion` (`componentVariant.ts`) hace lo siguiente:
1. **Ubica la versión más alta ya existente** (la de mayor número entre las que tienen su propio `.content.xml` — tolera huecos, ej. si solo existen `v1` y `v3` toma `v3` como la más alta) y **la duplica tal cual** para crear la versión nueva (`vN+1`) — mismo criterio que usa "Crear variante" para `v1`→`v2`: el usuario arranca la versión nueva con el contenido real de la anterior (HTL, diálogo, `_cq_editConfig`/`_cq_design_dialog`/`_cq_template` si los tuviera) en vez de una plantilla vacía, y la ajusta a mano desde ahí. La clientlib clásica, si la hay, no se toca — vive fuera de `components` y ya es compartida entre todas las versiones por convención de la extensión.
2. **El proxy se reescribe únicamente en `sling:resourceSuperType`** (mismo `.content.xml`, sin recrearlo) para que pase a apuntar a la versión nueva — el resto de sus propiedades (título, grupo, ícono, `allowedParents`...) quedan intactas, igual que en "Crear variante".

No pide ningún dato de formulario (nombre/título/grupo/estilos...) porque no crea un componente de cero — parte enteramente del contenido ya existente de la versión anterior. Tras crearla se muestra un mensaje con la ruta de la versión nueva y desde cuál se creó, y se auto-abren su `.html` y su diálogo (mismo criterio de apertura automática que el resto de flujos de creación). Si se cancela el modal, no se toca nada en disco. Verificado con un componente simulado de 2 versiones (con propiedades JCR extra en el proxy) confirmando que la versión más alta detectada es la correcta, que la versión nueva es un duplicado exacto de esa (no de una plantilla vacía), que el proxy pasa a apuntar a la versión nueva sin perder sus demás propiedades, y con el flujo completo del comando (stub de `vscode`) confirmando tanto la confirmación como la cancelación del modal.

### 3.10 Diálogos de componente — el corazón de la extensión (Bloque 19) — 🟡 MVP ampliado en v1.5.0/v1.7.0/v1.8.0/v2.1.8
**Comando "AEM: Editar diálogo..."** (clic derecho sobre la carpeta `_cq_dialog` de un componente — o de una página/plantilla, mismo mecanismo `_cq_dialog` — o directamente sobre su `.content.xml`) abre un panel dedicado (`vscode.window.createWebviewPanel`, no una vista de la barra lateral — el formulario con pestañas/agrupadores anidados necesita más espacio horizontal) con el diálogo representado como un árbol visual editable. **También abre el `.content.xml` crudo como pestaña de texto normal (agregado en v2.1.8, a pedido explícito)**, para que el usuario pueda decidir con cuál de los dos interactuar — el editor visual queda como pestaña activa al terminar, ya que sigue siendo la forma principal de trabajar el diálogo, pero el XML queda igual disponible. Aplica a las tres formas de llegar al editor: el comando de clic derecho, "AEM: Diálogo" (acceso rápido), y la apertura automática al crear un componente nuevo (ver 3.3, punto 8) — las tres pasan por la misma función `openDialogEditor`.

**Módulos internos** (`src/dialog/`):
- `fieldCatalog.ts`: catálogo de tipos disponibles en el selector "Agregar...". v1.4.0 traía 10; v1.5.0 lo amplía con 10 más a pedido explícito: selector de fecha (datepicker), grupo de opciones tipo radio (radiogroup), selector de ruta alternativo (pathbrowser), carga de archivo (fileupload), campo oculto (hidden), contraseña (password), selector de color (colorfield), interruptor/switch, encabezado estático (heading) y selector de tags — además de los ya existentes (pestaña, agrupador, texto, área de texto, RTE, numérico, selector de ruta, lista desplegable, casilla, multicampo). El modo "avanzado" con el catálogo COMPLETO de Granite UI (más tipos, de uso más raro) sigue pendiente para una versión posterior — es un recorte intencional, no un olvido.
- `dialogModel.ts`: convierte entre el árbol JCR real (`DocViewNode` de `sync/docview.ts`, reutilizado tal cual) y un **modelo simplificado** (`DialogTree`). Cambio de fondo en v1.5.0: el modelo ganó `hasTabs` — un diálogo **ya no se envuelve forzosamente** en una pestaña "General" sintética si el original no usaba pestañas (comportamiento de v1.4.0); ahora se representa fielmente sin pestañas (`items` planos) hasta que el usuario pide explícitamente "Agregar pestañas", momento en el que los campos existentes se mueven automáticamente a la primera pestaña. Simplificaciones que se mantienen:
  - Los layouts de columnas (`fixedcolumns`/`column`) se **aplanan** a una sola lista al cargar y **nunca se reintroducen** al guardar — un diálogo con 2 columnas queda en 1 columna después de editarlo con este panel. Es un tradeoff aceptado para no tener que construir también un editor de layout de columnas en esta primera versión.
  - Cualquier campo de un tipo **fuera del catálogo** ya presente en el diálogo se conserva como ítem "avanzado": se puede reordenar y eliminar, pero no editar en detalle — y su nodo XML original (incluidos sus propios hijos, ej. opciones anidadas) se preserva verbatim al guardar, para no destruir contenido que la extensión todavía no sabe interpretar del todo.
  - `select`/`radiogroup`: sus opciones (nodo `items` hijo con `text`/`value`/`selected` por opción) sí tienen editor dedicado (agregar/quitar filas, marcar cuál es la predeterminada) — ambos comparten el mismo editor de opciones.
  - `multifield`: solo soporta el caso simple — un único campo interno repetible (`composite` con múltiples sub-campos por fila queda para después).
  - `heading` no se enlaza a ninguna propiedad JCR (solo un texto estático `text`, sin `name`/`fieldLabel`); `hidden` solo lleva `name` + `value`, sin `fieldLabel` (no se muestra al autor) — ambos tienen su propio editor de propiedades reducido en vez del genérico etiqueta/nombre/descripción.
- `docviewSerializer.ts`: **inverso** de `docview.ts#parseDocView`. Reformateado en v1.5.0 a pedido explícito: la abertura de la etiqueta y su primer atributo van en la primera línea; si hay más de un atributo, los siguientes se listan uno por línea (indentados un nivel más que la abertura) con el `>` pegado al final del último; si hay 0 o 1 atributos el `>` va en esa misma primera línea; la etiqueta de cierre siempre va en su propia línea siguiente (nunca autocierre `/>`, aunque el nodo no tenga hijos) — se aplica a todo el árbol serializado, no solo a los campos agregados en la sesión de edición, para que el archivo quede formateado de manera uniforme.
- `dialogPanel.ts`: arma el HTML del panel. Toda la interacción (agregar/reordenar/editar/eliminar pestañas, agrupadores y campos, más "Agregar pestañas"/"mover a otra pestaña" nuevos en v1.5.0) ocurre en JS del lado del cliente sobre una copia en memoria del árbol simplificado (igual que el patrón ya usado en `compilePanel.ts`) — la conversión completa a/desde el árbol JCR real solo pasa por el lado de la extensión al abrir el panel y al guardar.

**Reglas de pestañas (nuevo en v1.5.0, a pedido explícito)**:
- Si el diálogo no tiene pestañas, aparece un botón **"+ Agregar pestañas"** en vez de la tira de pestañas. Al usarlo, los campos planos existentes se mueven automáticamente a una primera pestaña ("General") y desde ahí se puede seguir agregando pestañas hermanas con "+ Pestaña".
- **No se puede anidar una segunda estructura de pestañas dentro de una ya existente**: el tipo "Pestaña" se excluye a propósito del selector genérico de "Agregar..." en cualquier nivel (dentro de un agrupador, o de otra pestaña) — la única forma de crear pestañas es el botón dedicado, que siempre agrega hermanas de las existentes.
- Si se borran todas las pestañas (el botón ✕ de cada una), el diálogo vuelve automáticamente a modo "sin pestañas".
- **Mover un campo a otra pestaña**: cuando hay más de una pestaña, cada ítem (campo o agrupador) muestra un botón "↪ Mover a otra pestaña". Si hay exactamente 2 pestañas, el clic mueve el ítem directo a la otra (no hace falta elegir). Si hay más de 2, aparece un selector con las demás pestañas para elegir el destino antes de confirmar.

**Guardar**: escribe el `.content.xml` en disco automáticamente (sin un paso de confirmación aparte — así lo pidió el usuario) y, después, pregunta con un modal si se quiere subir el cambio ahora a Author/Publish, reutilizando `syncUris` (que para `_cq_dialog/.content.xml` ya hace el reemplazo total de la v1.3.0) — o dejarlo para más tarde y subirlo manualmente después.

**Pendiente para una versión futura** (no cubierto por el MVP): visibilidad condicional entre campos (`cq-dialog-showhide-target`), extensión de CSS/JS del diálogo vía `clientlib` propio, sincronización automática de propiedades nuevas con el modelo Sling del componente, y el catálogo "avanzado" completo (con el resto de tipos de Granite UI de uso más raro).

**Verificación realizada** (sin acceso a VS Code real ni a una instancia AEM): round-trip completo (`parseDocView` → `fromDocView` → editar el árbol → `toDocView` → `serializeDocView` → volver a parsear) contra fixtures de diálogo plano (sin pestañas) y con pestañas (3 pestañas), confirmando que un diálogo sin pestañas se guarda sin pestañas (ya no se le fuerza una "General" sintética) y que uno con pestañas conserva su cantidad y orden; además, creación de cada uno de los 10 tipos nuevos verificando su `sling:resourceType` y valores por defecto, y el nuevo formato de indentación de atributos. La interacción del panel en sí se probó cargando el HTML generado en un navegador headless (Playwright) con `acquireVsCodeApi` simulado: conversión de plano a pestañas con movimiento automático de los campos existentes, exclusión de "Pestaña" del selector genérico de "Agregar...", reversión automática a modo plano al borrar la última pestaña, y el flujo de "mover a otra pestaña" tanto con 2 pestañas (mueve directo) como con 3 (muestra selector).

**Comando adicional (v1.6.0): "AEM: Formatear XML"** — no forma parte del Bloque 19/20 en sí, pero nace directamente del trabajo de `docviewSerializer.ts`: expone ese mismo formateador como una operación independiente, aplicable a **cualquier** `.xml` de FileVault Document View del proyecto (no solo a los `.content.xml` de diálogo que abre el editor visual). Clic derecho sobre uno o varios `.xml` dentro de `jcr_root` (Explorador o editor) → "AEM: Formatear XML" — parsea el archivo, lo reserializa con el mismo estilo (abertura + primer atributo en la primera línea, atributos adicionales uno por línea indentados un nivel más con el `>` pegado al último, cierre de etiqueta siempre en su propia línea alineado con su abertura) y lo escribe de vuelta si hubo cambios (no toca el archivo si ya estaba formateado igual — operación idempotente). Módulo: `src/format/formatXmlCommand.ts`.
- **`reformatXml` extraída como función compartida (v2.1.9)**: la operación completa (parsear + fusionar namespaces + reserializar) se expone como una única función en `docviewSerializer.ts`, usada tanto por este comando como, desde v2.1.9, por la creación de componentes (ver 3.3) para que cada `.xml` generado salga ya formateado — sin duplicar la lógica de formateo en dos lugares.
- **Preserva namespaces propias del archivo**: hasta v1.5.0 el serializador siempre declaraba únicamente las 4 namespaces estándar (`jcr`/`sling`/`cq`/`nt`), sin importar cuáles tuviera el archivo original — al exponer el formateo como comando de propósito general esto se volvió un riesgo real (un `.content.xml` que además declarara `granite`, `dam`, `wcmio`, etc. las hubiera perdido silenciosamente al formatearse). Se agregó `extractRootNamespaces` (`sync/docview.ts`) para leer las namespaces reales del elemento raíz del archivo, y `mergeNamespaces` (`docviewSerializer.ts`) para combinarlas con las 4 estándar (que siempre se garantizan, por si el árbol usa esos prefijos) sin duplicar. El editor visual de diálogos (`dialogPanel.ts`) también se actualizó para usar este mismo mecanismo al guardar, por consistencia.
- Verificado con un fixture deliberadamente "desprolijo" (indentación inconsistente, atributos todos en una sola línea, namespace `granite` extra, RTE con `rtePlugins`/`uiSettings` anidados 5 niveles) confirmando namespace preservada, cero autocierres, y que cada etiqueta de cierre queda exactamente alineada con la indentación de su propia abertura en todo el árbol (verificado programáticamente con una pila de indentaciones, no solo visualmente); además pruebas de comando con selección múltiple, archivo no-`.xml` (se ignora con aviso, no error), archivo `.xml` inválido (reporta error sin tirar la extensión), y una segunda pasada sobre un archivo ya formateado (no reescribe nada).

**Nuevo comando (v1.7.0): "AEM: Diálogo"** — acceso rápido al mismo editor, pensado para el caso común de "agregar un campo más" sin abrir el panel completo. A diferencia de "AEM: Editar diálogo..." (solo Explorador, siempre abre el editor completo), este aparece con clic derecho **dentro del código** de un `.content.xml` de diálogo ya abierto en el editor (`editor/context`, mismo `when` que filtra `_cq_dialog`). Muestra un `QuickPick` con los 5 tipos más usados — Textfield, Pathfield, Checkbox, Select (dropdown), Multifield — más "Edición avanzada" (abre `openDialogEditor`, el panel completo, para cualquier caso más complejo). Flujo: pide la etiqueta (`InputBox`, opcional), resuelve dónde insertar el campo (raíz si el diálogo no usa pestañas; directo si tiene una sola pestaña; `QuickPick` de pestañas si tiene más de una), guarda el archivo con `createNewItem`/`toDocView`/`serializeDocView` (preservando namespaces igual que el editor completo) y ofrece subir el cambio a Author/Publish al toque. Módulo: `src/dialog/dialogQuickAdd.ts`.
- Guarda primero el documento si estaba abierto y sucio (`isDirty`), para no pisar cambios no guardados del propio archivo con la versión en disco al releerlo.
- Verificado con un stub de `vscode` (QuickPick/InputBox respondidos programáticamente) contra dos fixtures: diálogo plano (agrega multicampo directo a la raíz) y diálogo con 2 pestañas (pregunta a cuál, agrega en la elegida) — confirmando en ambos casos el XML resultante correcto.

**Corregido bug real de multicampo (v1.7.0)**: el nodo contenedor de un `multifield` simple llevaba, por error, su propia propiedad `name` con el MISMO valor que la de su campo interno repetido (`field`) — la convención real de Granite UI es que **solo el campo interno lleva `name`**, nunca el contenedor. Es una explicación plausible del aviso de "valor repetido" reportado al agregar un multicampo y probarlo en AEM real (el binding de formulario de Granite vería dos widgets apuntando a la misma ruta de propiedad). Corregido en `createNewItem` (`dialogModel.ts` y su copia cliente en `dialogPanel.ts`) con un caso especial temprano para `multifield` que construye el nodo contenedor sin `name` y su hijo `field` con `name` propio; el editor de propiedades oculta ahora el input genérico "Nombre de propiedad" para ítems `multifield` (su "nombre" real es el del campo interno, ya editable en el bloque `multifield-inner`). **Editar** un multicampo ya existente (cambiar el tipo/etiqueta/nombre de su campo interno) no tenía este bug — `getMultifieldInner`/`setMultifieldInner` ya operaban correctamente solo sobre el nodo `field`, así que crear y editar quedan ahora consistentes entre sí. Verificado con round-trip (crear → serializar → volver a parsear) confirmando que el contenedor nunca lleva `name` tras el ciclo completo.

**Nombres de tipo en inglés (v1.7.0)**: todos los `label` de `fieldCatalog.ts` se tradujeron de español a inglés (Textfield, Textarea, Richtext (RTE), Number field, Pathfield, Pathbrowser, Select (dropdown), Radio group, Checkbox, Switch, Multifield, Date picker, File upload, Color field, Password, Hidden field, Tags, Heading, Tab, Fieldset) — son los nombres con los que estos tipos de Granite UI se documentan y conocen normalmente, a pedido explícito para que sean más fáciles de identificar que una traducción libre.

**Errores de guardado en rojo (v1.7.0)**: en el panel del editor completo, el mensaje de estado tras guardar ahora distingue visualmente error de éxito — verde (`✔ Guardado`) o rojo (`✘ <mensaje>`) usando los colores de tema de VS Code (`--vscode-testing-iconPassed`/`--vscode-errorForeground`) — antes ambos casos se veían con el mismo estilo neutro, dificultando notar que algo había fallado.

**"Copiar cómo usarlo" por campo (v1.8.0, reubicado en v1.8.1)**: cada fila de campo tiene un ícono 📋 (a la izquierda de ✏️ "Editar", visible sin desplegar nada — reubicado ahí en v1.8.1 a pedido explícito, antes vivía dentro del editor expandido) que copia al portapapeles la expresión HTL típica para leer esa propiedad (`${properties.NOMBRE}`) junto con un comentario del tipo de dato esperado (String, Number, Boolean, Calendar, String[]...) — pensado para pegar directo en el `.html` del componente sin tener que adivinar cómo se llama la propiedad ni qué tipo devuelve. El tooltip del ícono (al pasar el mouse) muestra el texto exacto que se copiaría; al hacer clic, el ícono cambia brevemente a ✅ como confirmación.
- El tipo de dato varía según el tipo de campo (`typeForKind`/`usageNoteForKind` en `dialogPanel.ts`): `Boolean` para checkbox/switch, `Number` para campo numérico, `Calendar` (con sugerencia de `@ format=`) para selector de fecha, `String[]` para tags y multicampo, `String` con una nota aclaratoria para pathfield/pathbrowser y file upload. Un nombre de propiedad con caracteres fuera de `[A-Za-z0-9_:]` se copia con notación de corchetes (`${properties['nombre-raro']}`) en vez de notación de punto, para no generar una expresión HTL inválida.
- **Multicampo**: usa la propiedad del campo interno repetido (vía `getMultifieldInner`, no el contenedor — que a propósito no lleva `name` desde el fix de la v1.7.0). Al vivir en la fila (recalculado en cada `render()`), refleja el campo interno tal como quedó guardado la última vez que se cerró/reabrió su editor.
- Sin ícono para pestaña/agrupador/encabezado (no representan ninguna propiedad JCR). Los campos de tipo "avanzado" (no reconocido por el catálogo) también lo muestran si tienen un `name` legible en su nodo XML crudo, con una nota invitando a revisar el `sling:resourceType` real.
- El mensaje `copyToClipboard` se procesa del lado de la extensión con `vscode.env.clipboard.writeText` (no `navigator.clipboard` del lado del webview, menos confiable dentro del sandbox de VS Code).
- Verificado con Playwright sobre el HTML real generado por el panel: orden correcto del ícono en la fila (Subir, Bajar, Copiar, Editar, Eliminar), tooltip con el texto exacto, clic postea el mensaje `copyToClipboard` correcto, y ausencia del ícono en la fila de un encabezado — más una prueba directa del lado de la extensión confirmando la llamada a `vscode.env.clipboard.writeText` con el texto exacto recibido.

### 3.11 Editar diálogos + selección múltiple para tabs (Bloque 20)
La edición de **un solo componente** (abrir un diálogo ya existente y modificarlo) queda cubierta por el MVP de 3.10 — es el mismo panel, ya que "editar" y "crear campos nuevos en un diálogo existente" son la misma operación en este editor (agregar/quitar/reordenar sobre el árbol ya cargado).

Sigue pendiente (no cubierto todavía) el flujo de **selección múltiple** para unificar propiedades de varios componentes a la vez:
1. Click derecho sobre **uno o varios** componentes (VS Code permite selección múltiple nativa en el Explorer con Ctrl/Cmd+click o Shift+click; el `menu` `explorer/context` recibe todos los URIs seleccionados si el comando se registra sin filtro de `explorerResourceIsFolder` estricto) → "AEM Toolkit: Agregar propiedades…".
2. Si son **varios componentes seleccionados**: antes de abrir el editor se pregunta la estrategia de unificación:
   - **Pestañas (tabs)**: cada componente pasa a ser una pestaña dentro de un diálogo combinado (útil para un "componente contenedor" que agrupa variantes).
   - **Multifield**: las propiedades comunes se agrupan como un único campo repetible.
   - **Cancelar / tratar cada uno por separado**.

### 3.12 `data-sly-template` en `utils` (Bloque 4)
Formulario simple: nombre de la plantilla + lista de atributos que recibe (`data-sly-template.nombre="${@ attr1, attr2}"`). Se crea en `components/utils` del proyecto (ruta detectada, ej. `apps/gatesconnect/components/utils`).

### 3.13 Modularizar HTML (Bloque 8)
Al seleccionar texto en un `.html`, comando contextual con dos opciones: "Extraer a `data-sly-template`" (reemplaza la selección por `data-sly-call` y crea/agrega la plantilla en `utils` o en el mismo archivo) o "Extraer a archivo aparte" (crea `<nombre>.html` en la misma carpeta y reemplaza la selección por `<sly data-sly-include="<nombre>.html" />`, igual que `orderHistoryList.html` en gatesconnect-aem).

### 3.14 Reusar componente vía `data-sly-resource` (Bloque 9)
Sobre una línea vacía del HTL, `QuickPick` con buscador de todos los `resourceType` existentes en el proyecto. El **id** que el usuario escribe (ej. `btn`) se resuelve automáticamente a algo único: se escanea el archivo (y opcionalmente el resto del proyecto) por otros `data-sly-resource="<id>..."`/`data-sly-list` y se agrega un sufijo incremental (`btn-1`, `btn-2`…) — importante para ciclos `data-sly-list`, donde además se sugiere concatenar el índice de iteración (`btn-${itemList.index}`) en vez de un número fijo, para que no colisione entre iteraciones.

### 3.15 i18n desde texto seleccionado (Bloque 15)
Al seleccionar texto en HTL: pedir el nombre de la key i18n, luego un modal Webview con un campo de texto **por cada idioma detectado** en el proyecto (carpetas `i18n/<idioma>`), prellenando todos con el texto original seleccionado (el usuario solo edita los que quiera traducir). Se crea la entrada en cada diccionario y se reemplaza el texto original por `${'<key>' @ i18n}` (o `data-sly-text` según contexto). Si el cursor ya está sobre una key i18n existente, el mismo comando abre el modal en modo edición con los valores actuales por idioma.

### 3.16 Ir a modelo (Bloque 7)
`DefinitionProvider` de VS Code: al Ctrl/Cmd+click (o "Ir a definición") sobre el valor de `data-sly-use.model="com.foo.Model"`, resuelve la clase Java en `core/src/.../models/` y la abre.

### 3.17 Formatear HTL (Bloque 6)
`DocumentFormattingEditProvider` para `.html` de componentes: al detectar cierre de etiqueta o nueva apertura, aplica salto de línea + indentación (respetando `data-sly-*` como atributos, no como elementos). Mismo mecanismo que el formateador Prettier-based de `angular-schematics-free` (`format.ts`), pero con reglas propias para HTL en vez de Angular templates.

### 3.18 Diagnósticos en vivo (Bloque 21)
`DiagnosticCollection` que revisa el documento en cada cambio (`onDidChangeTextDocument`) buscando etiquetas sin cerrar y errores comunes de sintaxis HTL (`data-sly-*` mal escrito, comillas sin cerrar, `${}` sin cerrar), mostrando el subrayado rojo/amarillo nativo de VS Code (no requiere una extensión de "Error Lens" de terceros — los diagnósticos ya se muestran inline si el usuario tiene Error Lens instalado, y en el editor normal aparecen en el margen y al pasar el mouse).

### 3.19 Editar template de página existente (Bloque 12)
Vista de árbol o Webview para: agregar componentes permitidos a un `policy`/`structure`, editar propiedades de la página, cambiar el HTML base de la plantilla, agregar una clase distintiva al `<body>`/contenedor raíz. Cualquier cambio queda reflejado en los archivos reales, así que aparece automáticamente al compilar/desplegar.

### 3.20 Cache/exclusión de contenido (Bloque 22, opcional)
Si el proyecto trae configuración de dispatcher accesible (ver carpetas `*-dispatcher` junto a `AEM/`), ofrecer editar reglas de cache (`/cache/rules`) o exclusión (`/filter`) desde un formulario simple. Se marca como "si es posible" porque depende de que el dispatcher esté en el mismo workspace.

## 4. Configuración de la extensión (`aemToolkit.*`)

- `aemToolkit.defaultBuildScope`: `all` | `front` | `back` — ámbito por defecto al compilar.
- `aemToolkit.defaultInstallProfile`: perfil Maven usado si no se especifica otro.
- `aemToolkit.defaultSkipTests`: boolean.
- `aemToolkit.mavenExecutable`: `mvn` | `./mvnw` (autodetectado si existe `mvnw`, pero editable).
- `aemToolkit.savedBuildProfiles`: perfiles de compilación guardados por el usuario.
- `aemToolkit.componentsCreateCssJsByDefault`: boolean — si al crear componente se generan CSS/JS sin preguntar.
- `aemToolkit.maxDialogTabs`: número máximo de pestañas al crear un diálogo (default `10`).
- `aemToolkit.defaultLocales`: idiomas por defecto a ofrecer en el modal de i18n (autodetectados de `i18n/*` si no se define).
- `aemToolkit.componentsUtilsPath` / `aemToolkit.i18nPath` / `aemToolkit.namespace`: overrides de rutas si la convención del proyecto no coincide con la detectada automáticamente.
- `aemToolkit.sync.authorHost` / `aemToolkit.sync.authorPort`: host/puerto de la instancia Author usada por "AEM: Subir a Author" (default `localhost`/`4502`).
- `aemToolkit.sync.publishHost` / `aemToolkit.sync.publishPort`: host/puerto de la instancia Publish usada por "AEM: Subir a Publish" (default `localhost`/`4503`).
- `aemToolkit.sync.username`: usuario compartido para ambos destinos (default `admin`). La contraseña no vive acá — se configura con "AEM: Configurar credenciales de sincronización..." y se guarda en Secret Storage.
- `aemToolkit.javaHome`: ruta a la carpeta del JDK que deben usar las Tasks de Maven del panel de compilar. Configuración de **workspace** (`scope: resource`). Vacío (por defecto) = detección automática (ver `jdkSearchFolders`) o el JDK del sistema.
- `aemToolkit.jdkSearchFolders`: hasta 2 carpetas "contenedoras" de varios JDKs donde la extensión busca automáticamente la versión que el proyecto necesita cuando no coincide con la del sistema. Configuración de **workspace**.
